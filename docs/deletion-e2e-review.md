# 삭제·복구 구현과 실제 흐름 검증

검증일: 2026-09-14. [PRD](deletion-prd.md)를 먼저 확정·커밋한 뒤 구현했다.

## 결과

업무 읽기 화면의 **업무 삭제**, 업무/고객 수정 화면 및 할 일의 안전한 삭제, **휴지통 검색·종류 필터·내용 확인·복구**를 구현했다. 모든 삭제는 휴지통 이동이며 자동 비우기나 영구삭제는 제공하지 않는다.

업무 본문·물건 상세·매물 이벤트·복구에 필요한 원본 메모를 한 트랜잭션으로 보관한다. 활성 업무 제거와 영향 매물 재계산, 복구 시 관계 복원도 원자적으로 처리한다. 휴지통까지 전체 9개 테이블의 암호화 백업에 포함한다. 고객 참조와 자료 내용의 SHA-256 확인값, 트랜잭션 시점의 SQL 재검증으로 잘못된 삭제·복구를 막는다.

## 검증 환경

- 실제 Chromium 브라우저 + 배포용 Worker 빌드 + Wrangler 로컬 D1/R2.
- 별도 로컬 관리자와 합성 고객 2명, 두 매물에 연결된 등록/수정 업무, 확인할 일, 날짜 있는 합성 원본 메모와 원본 전용 메모.
- 테스트 서버는 `127.0.0.1:4173`이며 운영 DB·R2와 연결되지 않았다. 운영 고객이나 매물에 테스트 등록·삭제·복구를 수행하지 않았다.
- Playwright CLI로 화면의 실제 버튼을 눌렀다. 동시 변경은 같은 로컬 서버의 실제 수정 API, 네트워크 단절은 삭제 요청 중단, 느린 응답은 실제 요청을 지연시켜 재현했다. 정상 API 응답을 가짜 성공 응답으로 대체하지 않았다.

## 실제 브라우저 E2E

| 흐름 | 확인 결과 |
| --- | --- |
| 업무일지 검색 → 읽기 → 삭제 확인 → Esc 취소 | 연결된 두 매물과 원문 표시. 취소에 첫 초점. 읽던 화면과 검색어 유지 |
| 수정 중 내용 입력 → 삭제 확인 → 취소 | 저장된 내용과 초안을 구분. 미저장 입력 유지. 수정 취소는 원래 읽기 화면으로 복귀 |
| 업무 삭제 → 목록과 연결 자료 확인 | 검색 결과 1건→0건. 업무 상세 404, 업무 검색·고객별 이력·월간 달력 조회·통합검색에 삭제 업무 없음 |
| 두 매물 재계산 | 잘못 입력한 두 매물 가격 9억이 각각 이전 3억/4억으로 복귀. 다른 업무·고객은 유지 |
| 원본 메모 처리 | 삭제한 업무 내용은 현재 매물 본문/원본 메모에서 제외. 관계없는 원본 전용 메모 유지 |
| 휴지통 종류/주소 검색 → 내용 확인 → 복구 | 원래 업무 ID·날짜·두 물건과 이력 복원. 가격 9억으로 재계산. 원본 전용 메모 유지 |
| 연결 고객 삭제 | 이유를 표시하고 실행 버튼 비활성화. 연결 없는 고객은 삭제→검색 0명→복구→1명 확인 |
| 홈의 할 일 삭제·복구 | 홈에서 빠지고 휴지통에서 복구. 원래 기한·고객 연결·메모 보존 확인 |
| 확인 후 다른 기기의 실제 수정 | 삭제 409. 오래된 확인값으로 재실행 차단. 최신 내용 다시 읽은 뒤 진행 가능 |
| 네트워크 오류 | 성공으로 안내하지 않음. 원래 자료 유지. 다시 시도 가능. 오류 후 Esc도 뒤의 업무 화면을 닫지 않음 |
| 삭제 더블클릭·처리 중 Esc | 실제 DELETE 요청 1회. 처리 중 취소 비활성화, Esc로 창을 닫지 않음 |
| 매물 이력에서 마지막 업무 삭제 | 사전 경고 표시. 현재 매물 제거 후 주소 오류가 아닌 빈 이력과 복구 안내 표시 |
| 두 업무 삭제 후 하나씩 복구 | 첫 업무만 복구할 때 아직 휴지통에 남은 다른 업무/원본 메모가 재등장하지 않음. 이후 나머지도 복구 |
| 휴대폰 390×844 + 큰 글씨 | 확인창·휴지통의 가로 잘림 없음. 하단 조작 버튼 접근 가능. 긴 본문은 줄바꿈/스크롤 |

화면 증거는 개발 작업공간의 `output/playwright/deletion-geBX0y/`에 보관했다. `delete-confirm-desktop.png`, `delete-mobile-large.png`, `trash-mobile-large.png` 및 단계별 스냅샷은 모두 합성 자료이다. 로컬 인증 설정과 DB/백업 저장소는 Git에 포함하지 않는다.

## 검증 중 발견해 추가로 고친 문제

1. 기존 삭제는 수정창 하단에 숨어 있었고 영구삭제였다. 읽기 화면에 진입점을 추가하고 휴지통으로 통일했다.
2. 삭제된 엑셀 메모가 원본 보관 영역에서 다시 보이거나 마지막 매물의 원본이 사라질 수 있었다. 삭제 대상에 해당하는 부분만 분리하고 원본은 복구 스냅샷에 보존했다. 날짜/업무구분만 같은 다른 메모를 지우지 않는다.
3. 확인창 Esc가 부모 편집/읽기 창까지 닫았다. 특히 요청 중 버튼이 비활성화되어 초점이 밖으로 빠진 뒤에도 재현됐다. 네이티브 모달과 창 캡처 단계의 키 처리로 차단하고 실제 실패 후 취소까지 재검증했다.
4. 마지막 업무를 삭제한 매물을 다시 읽으면 주소가 틀렸다는 오류가 나왔다. 정상적인 빈 상태와 휴지통 복구 안내로 변경했다.
5. 화면에서 `Failed to fetch`만 표시되던 오류를 한글 연결 안내로 바꿨다. 응답 유실 시 이미 처리됐을 가능성도 설명한다.
6. 휴대폰 큰 글씨에서 위험 동작 이름이 한 글자씩 쪼개지지 않게 단어 단위 줄바꿈을 적용했다.

## 자동 검증과 남는 범위

- 전체 자동 회귀검사 **390개 통과**, TypeScript 검사·ESLint·배포 빌드 통과.
- 실제 SQLite SQL로 배치 중 실패의 전체 롤백, 같은 초 수정/읽기-쓰기 경합, 중복 요청, 복구 충돌, 고객의 활성/휴지통 의존성, 새 원본 메모 보존 등을 검증했다.
- 백업 보안 검사는 로그인 401, 교차 출처 403, 변경 전 백업 실패 시 503과 쓰기 중단, 실제 AES-GCM 암호화/복호화 후 휴지통과 활성 자료 보존을 확인했다.
- 완료된 할 일 복구, 최대 10개 매물, 휴지통 페이지/실패·늦은 응답 처리는 자동 검사로 검증했다. 실제 브라우저에서는 2개 연결 매물과 소량 휴지통을 사용했다.
- 운영에서 파괴적 E2E나 전체 DB 복원 시험은 하지 않았다. 모든 기기/브라우저와 장기간 대량 사용까지 오류가 없다는 보증은 아니다.

## 추가로 유의미한 개선

이번에 필요한 **복구**, **연결 영향 안내**, **동시 변경 차단**, **미저장 초안 보호**는 함께 구현했다. 다음 우선순위는 삭제가 아니라 **수정 전 버전 복원**과 **동시 편집 덮어쓰기 방지**다. 현재 수정 자체는 마지막 저장이 앞선 변경을 덮을 수 있으므로 별도 설계가 필요하다.

일괄삭제·영구삭제는 자료 손실 위험이 커 이번에는 추가하지 않았다. 또한 접속 없는 날에도 실행되는 예약 백업과 외부 장소의 별도 백업은 휴지통과 다른 보호 수단이다. 현재 접속 시 일일 백업·변경 전후 백업을 유지하며, 정시 예약 백업이나 무기한 서버 이용을 보장하지 않는다.
