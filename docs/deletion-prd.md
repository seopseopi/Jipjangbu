# 삭제·휴지통 PRD

작성: 2026-09-14 · 상태: 구현 및 로컬 E2E 검증 완료 · [검증 보고서](deletion-e2e-review.md)

## 1. 문제와 목표

사용자는 잘못 입력한 업무를 삭제할 수 없다고 느낀다. 실제로 업무·고객 수정 창 하단과 할 일에는 삭제가 있지만, 업무 읽기 화면에서는 보이지 않는다. 현재 API는 영구삭제이며 변경 전 암호화 백업 외에 사용자가 직접 복구하는 방법이 없다.

목표는 삭제를 찾기 쉽게 만들면서, 한 번의 실수로 중요한 자료를 잃지 않게 하는 것이다. 기록을 누르면 내용을 먼저 읽는 기존 흐름, 검색 조건과 목록 복귀, 여러 매물의 연결 관계를 유지한다.

## 2. 이번 범위

| 대상 | 정책 |
| --- | --- |
| 업무 기록 | 읽기 화면과 수정 화면에서 단건 삭제. 업무·물건 상세·매물 이력을 함께 휴지통에 보관하고 현재 매물을 재계산한다. |
| 고객 | 연결된 업무나 복구 대기 기록 등 의존 관계가 없을 때만 휴지통으로 이동한다. 삭제 불가 이유를 먼저 안내한다. |
| 챙겨야 할 일 | 기존 삭제 버튼을 유지하되 휴지통 이동과 복구를 지원한다. |
| 매물 | 업무 이력으로 만들어지는 자료이므로 매물 통째 삭제 버튼을 추가하지 않는다. 잘못된 업무는 해당 업무 삭제, 정상적인 종료는 매물취소 등 업무 기록을 사용한다. |
| 분류·설정 | 이번에는 변경하지 않는다. 업무 삭제와 설정 제거를 섞지 않는다. |

일괄 삭제, 휴지통 영구삭제·자동 비우기, 전체 DB 복원, 수정 버전 전체 감사 로그는 제외한다. 휴지통은 자동으로 비우지 않는다.

## 3. 주요 사용자 흐름

1. 업무일지·홈·달력·매물/고객 이력에서 업무 내용을 연다.
2. 읽기 화면의 **업무 삭제**를 누른다. 수정 화면의 삭제도 같은 확인 절차를 사용한다.
3. 삭제 확인 창에서 고객, 업무일, 업무구분, 내용, 연결 매물과 영향 범위를 확인한다.
4. **취소**는 아무것도 바꾸지 않는다. **휴지통으로 이동**을 명시적으로 눌러야 실행한다.
5. 성공하면 삭제한 기록을 닫고 원래 목록·이력·홈·달력을 갱신한다. 검색 조건과 목록 범위는 가능한 한 유지한다.
6. **휴지통**에서 삭제일 최신순으로 업무·고객·할 일을 구분해 찾고 내용을 확인한 뒤 **복구**한다.
7. 복구된 업무는 원래 업무일과 순서로 돌아온다. 다른 업무가 만든 최신 가격·상태를 과거 값으로 덮지 않는다.

고객과 할 일도 대상 정보를 보여주는 확인 절차를 거친다. 고객의 경우 지울 수 없는 이유와 먼저 정리할 연결 항목을 알려준다. 수정 중인 초안은 저장된 기록과 구분하고 삭제 취소 시 입력을 유지한다.

## 4. UX·오류 처리

- 목록의 행 클릭은 계속 읽기이며 즉시 삭제하지 않는다. 삭제 버튼은 수정과 구분되는 보조 위험 동작으로 제공한다.
- 여러 매물이 연결되면 모든 주소와 개수를 표시하고, 이 업무에 연결된 모든 매물 이력이 함께 제거됨을 설명한다. 일부 매물만 지우려면 업무 수정의 **이 물건 빼기**를 사용하도록 안내한다.
- 마지막 매물 업무가 사라지면 현재 매물이 목록에서 없어질 수 있다. 고객 자체와 다른 업무는 삭제하지 않는다.
- 네트워크/백업 오류 시 성공으로 안내하지 않고 다시 시도할 수 있게 한다. 삭제 후 목록 갱신만 실패한 경우 삭제 실패와 구분한다.
- 처리 중 중복 클릭과 확인 창 닫기를 막는다. 확인 창의 초기 초점은 취소 등 안전한 동작에 둔다. Esc는 처리 전에는 취소이며 초점은 원래 화면으로 돌아온다.
- 확인한 뒤 다른 기기에서 기록이 변경되면 삭제를 거부하고 최신 내용을 다시 확인하게 한다. 초 단위 저장 시각만으로 변경 여부를 판정하지 않는다.
- 휴지통은 검색·유형 필터·빈 상태·오류·재시도를 제공한다. 복구는 명시적인 확인 후 실행한다.

## 5. 데이터 원칙

- 새 휴지통 표에 대상 종류, 원래 ID, 삭제일, 표시 정보, 복구용 원본 스냅샷을 저장한다.
- 업무 스냅샷은 업무 본문, 모든 물건 상세, 매물 이벤트의 ID·날짜·순서, 필요한 매물 원본 메모를 보존한다.
- 휴지통 저장, 활성 자료 삭제, 영향 매물 재계산은 하나의 원자적 작업이다. 어느 단계든 실패하면 전부 취소한다.
- 복구도 원본 관계 복원, 매물 재계산, 휴지통에서 제거를 하나의 원자적 작업으로 처리한다. 현존하는 동일 ID의 자료나 다른 사용자가 바꾼 자료를 덮어쓰지 않는다.
- 고객을 삭제해서 휴지통 업무를 복구할 수 없게 만들지 않는다. 활성 기록과 복구 대기 기록의 참조를 검사한다.
- 삭제한 엑셀 업무가 원본 보관 메모를 통해 다시 현재 이력에 나타나는 문제를 방지한다. 원본 자체는 복구 스냅샷 또는 원본 보관 데이터로 보존하고, 다른 원본 전용 메모는 손상시키지 않는다.
- 기본 목록·검색·통계·일정·고객 이력은 활성 자료만 사용한다. 휴지통은 별도 조회한다.
- 휴지통과 복구 경로도 기존 로그인·동일 출처 검사·변경 전후 암호화 백업의 보호를 받는다. 새 표를 전체 백업에 포함한다.

## 6. API 계약

- `GET /api/deletions/preview?type=work|customer|followup&id=...`: 저장된 대상 요약, 모든 영향 매물, 경고/삭제 불가 이유, 변경 확인용 `revision`을 반환한다.
- 기존 대상별 `DELETE`는 `revision`을 받아 직접 영구삭제 대신 휴지통으로 이동한다. 최신 자료와 일치하지 않으면 `409`, 없는 대상은 `404`, 미확인은 `400`으로 처리한다.
- `GET /api/trash`: 삭제일 최신순 목록, 유형/검색 필터와 페이지 조회. 목록에는 전체 내부 스냅샷을 싣지 않는다.
- `GET /api/trash/:id`: 복구 전 확인할 내용과 영향 정보를 반환한다.
- `POST /api/trash/:id/restore`: 충돌·참조 관계를 검증한 뒤 복구한다. 동일 작업 재실행이나 같은 ID의 현존 자료를 안전하게 처리한다.
- 계약의 세부 타입은 공통 타입으로 관리한다. 서버가 권한·대상·변경 여부를 최종 판정한다.

## 7. 인수 기준과 테스트

자동 API/SQL 검증: 원자적 이동·복구, 이전 매물 상태 복원, 마지막 이력, 여러 매물, 원본 메모 보존, 잘못된/누락된 revision, 같은 초 수정 경합, 복구 충돌, 고객 의존성, 중복 요청, 백업 보호.

로컬 격리 DB/R2의 합성 자료와 실제 브라우저로 다음 E2E를 수행한다. 운영 데이터에는 등록·삭제·복구 테스트를 하지 않는다.

1. 업무일지에서 내용 보기 → 삭제 취소 → 본문/목록 보존.
2. 업무 삭제 확인 → 휴지통 이동 → 목록·검색·고객/매물 이력·달력에서 제거 확인.
3. 휴지통에서 내용 확인 → 복구 → 원래 날짜·주소·가격·여러 매물 관계 확인.
4. 수정 중 삭제 취소 시 초안 보존. 이력에서 지워도 원래 목록으로 복귀.
5. 연결된 고객 삭제 차단, 연결 없는 고객 삭제·복구.
6. 할 일 삭제·복구 및 기존 완료/기한 정보 보존.
7. 확인 후 다른 변경이 발생한 대상의 삭제 거부. 네트워크 실패 시 재시도, 중복 클릭 방지.
8. 좁은 화면과 큰 글씨에서 삭제 확인/휴지통을 읽고 조작할 수 있으며 위험 버튼이 잘리지 않음.

검증 중 발견한 실제 흐름의 결함은 수정 후 재검증하고, 결과·추가 권장 사항·미검증 범위를 별도 보고서에 기록한다.
