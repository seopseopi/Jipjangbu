# 로딩·업무 창 열기 개선 검증 — 2026-09-14

## 범위와 결과

홈 최초 조회, 업무 등록·수정 준비, 창 복귀 갱신, 서버 DB 준비, 고객명부·매물·분류·통합검색 조회를 개선했습니다. 업무 삭제·휴지통·복구와 변경 전후 암호화 백업은 유지합니다. 운영 업무 자료는 수정하지 않았습니다.

`npm test`의 타입 검사·배포 빌드·회귀 검사 **408개 통과**, `npm run lint` 통과. 기존 390개 검사에 초기화 중단, 느린 창 열기, 명부 경합, 창 복귀와 최신성, 쿼리 결과 보존 검사가 추가됐습니다.

## 실제 브라우저 흐름

배포용 빌드를 격리된 로컬 Worker·D1·R2에서 실행하고, 합성 자료로 Chromium과 Playwright CLI를 사용했습니다. 운영 DB·백업 버킷과 연결하지 않았으며 업무 저장·삭제 없이 조회와 창 열기를 검증했습니다.

| 시나리오 | 확인 결과 |
|---|---|
| 처음 홈 열기 | `/api/bootstrap`, `/api/lookups`, 홈 할 일 조회만 발생. 전체 고객명부 조회 없음 |
| 고객명부 응답을 보류한 뒤 새 업무 클릭 | 준비창이 먼저 표시되고 미완성 입력 폼은 열리지 않음. 로컬 확인 36ms는 운영 속도 보장값이 아님 |
| 준비창에서 Esc | 창이 닫히고 원래 등록 버튼으로 포커스 복귀 |
| 취소 후 명부 응답 도착 | 취소한 창이 다시 나타나지 않음. 다시 클릭하면 입력창 하나만 정상 개방 |
| 업무 읽기 → 수정 준비 → Esc | 원래 읽기창 유지, 수정 버튼으로 포커스 복귀. 늦은 응답으로 수정창이 재개방되지 않음 |
| 명부 응답 보류 중 focus 이벤트 6회 | 진행 중 요청을 취소하지 않음. 기존 조회 1회 + 완료 후 최신 조회 1회로 합쳐짐 |
| 창 복귀와 입력 준비가 겹침 | 업무구분과 고객 선택 결과가 채워진 상태로 사용 가능 |
| 명부 API 503 합성 오류 → 다시 불러오기 | 오류·재시도 표시, 빈 입력 폼은 표시하지 않음. 재시도 1회로 고객·업무구분 복구 |

합성 503에 따른 브라우저 네트워크 오류 1건은 의도한 테스트입니다. 테스트 도구의 이벤트 수집 콜백에서 세션이 종료된 실행 2건은 성공 판정에 넣지 않았고, 수집 방식을 바꿔 새 세션에서 해당 흐름을 다시 통과시켰습니다.

## 수치 해석

- 전체 고객명부 조회를 홈에서 제거했습니다. 기본 조회 3개 → 2개이며, 홈 할 일 조회까지 포함하면 4개 → 3개입니다. 명부가 1,000명을 넘을 때의 추가 페이지 조회도 업무 폼 사용 시점으로 이동합니다.
- 분류는 D1 호출 2회 → batch 1회, 통합검색은 3회 → batch 1회입니다. HTTP 요청 수가 아니라 서버 내부 DB 호출 수입니다.
- 합성 고객 4,000명·업무 160,000건의 명부 SQL 중앙값은 로컬 실행에서 **28.91 → 3.80ms**였습니다. 네트워크·서버 기동·화면 그리기를 포함하지 않으며 운영 전체 속도 개선 배수로 해석하지 않습니다.
- 초기 정적 의존성 크기는 **581,361 → 582,780B**, gzip 합계 **172,087 → 172,441B**입니다. 준비창과 오류 처리를 추가해 소폭 증가했으며, 이번 개선은 코드 다운로드량 축소가 아니라 불필요한 데이터 조회와 취소 반복을 줄이는 작업입니다. HTML·이미지·전역 CSS·폰트를 포함한 총 다운로드량은 아닙니다.
- 운영 로그의 장시간 대기·취소를 확인했지만, 동일 네트워크 조건의 배포 전후 전체 로딩 시간 비교는 하지 않았습니다. 운영 속도를 특정 배수로 보장하지 않습니다.

## 유지한 안전장치

로그인·세션·권한 검사, 저장 전후 캐시 무효화, 늦은 수정 전 응답 차단, 전체 명부 페이지 조회, 삭제 미리보기·복구, 9개 업무 테이블 백업과 백업 실패 시 변경 차단을 유지합니다. 자세한 구조와 재현 방법은 [성능 개선 기록](performance.md)을 참고하세요.
